- 検索だけを実行して見つかったページと、その本文で確認できたこと：

  ベクトル検索・Graph検索では、`lec02-main-p052`を含む

- 取得した情報が足りなかった例、取得できたのに回答へ使えなかった例：

  今回の質問については、4方式とも必要な根拠を取得し、
  LoRAとQLoRAの主な違いを説明できた。
  明確な根拠不足による回答失敗は確認されなかった。

  一方、全文投入方式では質問に直接関係しない資料も
  大量に入力され、実際に回答で引用されたのは
  主として第2回の関連ページだった。

  Tree方式では、目的のページに到達するまでに

  今回の比較的単純な質問では、

- 今回の用途に採用したい方式と、その理由・比較条件の限界：

  今回の用途にはベクトル検索方式を採用したい。

  4方式とも適切な回答を生成できたが、
  ベクトル検索方式は入力トークン数が2,045と最も少なく、
  生成API推定費用も$0.001276で最小だった。

  全文投入方式の推定費用$0.035825と比較すると、
  約96.4%の削減となった。

  実行時間についてはGraph方式が3.89秒で最短だったが、
  ベクトル検索方式も4.04秒であり、
  今回の用途では費用と回答品質のバランスがよいと判断した。

  ただし、全文投入と他の方式では対象資料の範囲が異なる。
  また、同じ質問について各方式を1回ずつ実行した結果であり、
  回答品質や処理時間の一般的な優劣を断定することはできない。

- 気づき・疑問：

  基盤モデルに大量の資料を渡すことが、
  必ずしも効率的な回答につながるわけではないと分かった。

  今回はベクトル検索によって必要な根拠を少ない
  トークン数で取得でき、全文投入に比べて
  生成APIの推定費用を大幅に抑えられた。

  一方、TreeやGraphは複数の章や関連概念を
  横断する質問で有効になる可能性がある。

  RAGでは検索結果の量だけでなく、
  取得した情報が質問の根拠として十分かどうかを
  確認することが重要だと学んだ。

## 宿題

- 取り組んだレベル：
  基礎

- やったこと（変更したファイル・設定・処理、または設計した取得方法）：

  `app/config.py` の `RAG_TOP_K` を5から3に変更し、
  ベクトル検索で取得する最大ページ数を減らした。

  検索件数の変更によって、ツール呼び出し、
  回答内容、引用根拠、処理時間、トークン数、
  生成API推定費用がどう変化するかを比較した。

- 比較した質問と、固定した条件（モデル・対象資料など）：

  質問：「LoRAとQLoRAの違いは？」

  - モデル：gemini-3.5-flash-lite
  - 対象資料：第1〜3回の本講義資料
  - 検索方式：ベクトル検索
  - 実行方法：`app.agent --trace`
  - 変更した設定：`RAG_TOP_K`（5→3）

  質問、モデル、対象資料、その他の指示は変更せず、
  検索件数のみを変更した。

- 結果（変更前後の回答・根拠、`--trace`の出力、時間・トークン数・生成API推定費用など）：

  | 比較項目 | 変更前（TOP_K=5） | 変更後（TOP_K=3） |
  |---|---|---|
  | ツール名 | search_materials | search_materials |
  | ツール引数 | LoRA QLoRA 違い | LoRA QLoRA 違い |
  | ツール呼び出し回数 | 1回 | 1回 |
  | 回答内容 | LoRAは差分行列を学習、QLoRAは4bit量子化を追加 | 同じ主要な違いを説明 |
  | 引用根拠 | 第2回PDF p.51〜52 | 第2回PDF p.51〜52 |
  | 実行時間 | 4.57秒 | 3.75秒 |
  | 入力トークン | 2,993 | 2,993 |
  | 出力トークン | 196 | 160 |
  | モデル応答回数 | 2回 | 2回 |
  | 生成API推定費用 | $0.001388 | $0.001298 |

  実行時間は4.57秒から3.75秒となり、
  生成API推定費用は約6.5%減少した。

  ただし、入力トークン数は変更前後とも2,993であり、
  引用根拠も変化しなかった。

  そのため、今回の結果だけでは検索件数を減らしたことが
  処理時間や費用の削減に直接寄与したとは断定できない。

- 改善した例と、残る失敗・制約：

  今回の質問では、検索件数を減らしても、
  LoRAとQLoRAの主要な違いについて適切に説明できた。

  一方、必要な根拠が検索結果の下位に含まれる場合には、
  検索件数を減らすことで重要な情報を取得できなくなる
  可能性がある。

  また、比較は1つの質問に対する各1回の実行であり、
  応答時間や出力トークン数にはモデル実行時の変動も
  含まれるため、一般的な性能差を結論付けることは難しい。

- 気づき・疑問：

  RAGの検索件数は、多ければよいわけでも、
  少なければよいわけでもないと理解した。

  必要な根拠を確保しながら、入力トークン数や
  処理時間を抑える設定が重要である。

  今回は検索件数を減らしても回答品質を維持できたが、
  複数のページや講義を横断する質問でも同様の結果に
  なるかを検証する必要があると感じた。

  今後は、質問の種類に応じて検索件数を調整する方法や、
  ベクトル検索とTree・Graph検索を組み合わせる方法も
  検討したい。
